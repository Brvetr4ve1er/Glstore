# GLstore — UX Report

**Audit date:** 2026-07-31 · **Branch:** `gaming-store` @ `760b8b7` · Read-only audit — no source file modified.
**Method:** every finding below was read from source (file:line cited) and walked as a real user journey through the actual code, not the docs. **CONFIRMED** = I read the code end-to-end and can point at the exact lines that prove it. **SUSPECTED** = inferred, flagged as such. I did not re-report the four `store_id` bugs or the six just-landed multi-store commits — those are covered in `audit/Architecture.md`. Where my findings overlap an existing architecture finding, I trace it forward into its *user-facing* consequence, which the architecture audit didn't do.

Storefront copy is in French throughout (correctly, for an Algerian consumer audience). Admin copy is in English except one page. Both are noted below.

---

## 0. Executive summary

The shopper journey (land → browse → filter → product → cart → checkout → confirmation → track) is visually polished, has good loading/empty states, and gets the *French-language, COD-first, wilaya-shipping* framing right almost everywhere. But it makes three promises the system cannot keep: a shipping fee that will never be calculated (**C3**), a delivery timeline that can never advance past "confirmed" (**C1**), and error messages that lapse into raw English/UUIDs at the exact moment of highest anxiety — submitting payment info-free personal data and waiting for a confirmation (**H1**).

The operator journey (login → find a product → fix it → approve images → manage an order) is where the sharpest problems live. An operator opening any order to call the customer and arrange delivery **cannot see the customer's name, phone, or address anywhere in the app** (**C2**) — and even if they could call them, **there is no button anywhere to record that the order was packed, shipped, or delivered** (**C1**, shared root cause with the shopper-side symptom). The multi-store picker — the newest, most prominent admin feature — silently fails to switch the product catalog it's supposed to control (**H2**).

None of this requires new features to be invented from scratch: the DB columns (`shipping_address`, `shipped_at`, `delivered_at`), the enum values (`PACKED`, `SHIPPED`, `DELIVERED`), and the read patterns (`customers` table, `require_admin_store_for`) already exist elsewhere in the codebase. These are finish-the-wiring bugs, not architecture gaps — which is good news for how fast they can be fixed.

## 1. Shopper journey — land → browse → filter → product → cart → checkout → confirmation → track

### Land (Home) & browse/filter (Catalog, FilterSidebar)
Solid. Skeleton shimmer while loading (`Catalog.tsx:117-122`, `Home.tsx:145-150`), a real empty state with a reset-filters CTA (`Catalog.tsx:126-130`), sticky filter sidebar with brand/price/stock facets backed by real endpoints (`FilterSidebar.tsx`), URL-independent state that resets pagination on filter change (`Catalog.tsx:28`). Price formatting uses `Intl.NumberFormat('fr-DZ', {style:'currency'})` correctly (`storefront/src/lib/format.ts:8-16`). No findings worth flagging here.

### Product detail
Good information hierarchy: gallery, variant picker, stock badges ("Plus que N !" urgency framing when ≤3 left, `StockBadge`), LLM-generated editorial content (pros/cons, buyer-fit, verdict) rendered defensively (only shown if present). One recurring note, see **L2/C3** below: the price block's subtitle "TVA incluse · livraison calculée à la commande" (`ProductDetail.tsx:232`) sets an expectation that is never fulfilled anywhere downstream.

### Cart
Genuinely good engineering: live re-validation against `/offers/availability` on every visit (`Cart.tsx:24-30`), with inline per-item warnings (stock reduced, price changed, item removed) that persist on screen rather than only flashing as a toast (`Cart.tsx:160-168` renders `warnings[]` under each line — the ephemeral `toast()` calls at `:71-73` are a *supplement*, not the only signal). This is the single best-executed piece of the shopper journey.

- **[LOW] L2 — Cart empty-state promises a discount rule that doesn't exist.** `Cart.tsx:85` and the empty-cart `EmptyState desc` both say *"La livraison est offerte dès 50 000 DZD"* (free shipping from 50,000 DZD). Grepping `api/services/orders.py` and `api/models/schemas.py` for any subtotal-based shipping waiver finds nothing — `shipping_cost` is a flat client-supplied `Decimal` defaulting to `0` (`schemas.py:122`) with no threshold logic anywhere. Because of **C3** below, shipping is *always* 0 regardless of cart size, so the "free above 50K" claim is currently unfalsifiable and also meaningless.

### Checkout — the highest-friction, highest-stakes step
Form UX itself is fine: French validation messages, Algerian phone regex (`PHONE_RE` at `Checkout.tsx:30`), 58-wilaya `<select>` (`WILAYAS`, `storefront/src/lib/wilayas.ts`), COD explained in plain language, submit button shows a spinner via `loading={mut.isPending}`. Three real problems live here:

- **[CRITICAL] C3 — The checkout "Total" is a number the system can never actually charge or update.** `Checkout.tsx` builds its `OrderCreateInput` DTO (`:93-107`) and never sets `shipping_cost`; the schema default is `Decimal("0")` (`api/models/schemas.py:122`). The UI shows *"Livraison — Calculée par l'agent"* (`Checkout.tsx:252`) right next to a Total that is, in fact, final and already computed as subtotal-only (`:256`). I traced the "agent will calculate it" promise all the way through: there is no `PATCH /orders/{id}` endpoint anywhere in `api/routes/orders.py` (only `create`, `confirm`, `cancel`, `get_one`, `list_orders` exist), and the admin's `OrderDetail.tsx:143` renders `shipping_cost` as a **read-only** row — there is no input, no save button, nothing an "agent" can use to add a delivery fee after the call. The number the customer sees at checkout is the number they will be asked to pay, full stop, and no one in the system can ever change it. This is either a missing feature (build shipping calc) or a copy bug (stop promising it) — see Deeper Changes.
- **[HIGH] H1 — Checkout error messages are raw English, sometimes containing UUIDs, shown to a French-speaking customer.** `Checkout.tsx:48` does `onError: (e) => toast.error(e.message)` with zero translation layer. Trace the failure modes that reach this: `api/services/orders.py:106` `f"offers not found: {missing}"` (a raw UUID list), `:109` `f"offer {oid} is inactive"` (raw UUID), and the stock-race case is worse — `fn_reserve_stock` in `db/migrations/006_store_scope_orders.sql:42-44` raises `'reserve_stock: insufficient stock (have %, need %)'` as an **uncaught** Postgres exception (no `try/except` around the call in `orders.py:181-187`), which the global middleware catches and converts to `{"error": "internal_error"}` (`api/main.py:131-133`) — still English, still generic, still unhelpful right when a customer's cart item just sold out from under them. **Confirmed contrast**: `OrderTracking.tsx:115` gets this right — it ignores the raw backend error entirely and shows a hardcoded French message. The pattern exists in the codebase; it just wasn't applied to the one flow where a failure is most costly (an abandoned checkout).
- **[MEDIUM] M2 — "Ghir Laffaire" (the old, pre-GLAIVE brand) leaks into `<title>`/meta description on exactly the pages a shopper is most likely to bookmark, refresh, or share a link to.** Confirmed via grep: `Checkout.tsx`, `Cart.tsx`, `OrderConfirmation.tsx`, `OrderTracking.tsx`, `SearchResults.tsx` all pass `"Ghir Laffaire"` into their `<SEO description=…>` prop, while every visible on-page element (hero, nav, footer, brand logo) is fully "GLAIVE." A shopper who glances at the browser tab mid-checkout, or a link preview shared in a group chat for "hey I ordered this," shows a brand name that appears nowhere else in the product.

### Confirmation
Warm, clear success state with a 3-step "what happens next" strip (call → ship → pay-at-door, `OrderConfirmation.tsx:77-91`) and graceful degradation if `location.state` is lost on refresh (falls back to an ID-only view, `:71-75`). The promises made here ("Livraison 48h", "Appel sous 24h") are real UI commitments — see **L3**.

### Track order
Best-in-class error handling in the whole storefront (see H1 contrast above) and a clean 4-step visual timeline. Its one weakness isn't its own fault — see **C1**: for any real order today, this timeline structurally cannot progress past step 2 ("Confirmée") because nothing in the backend ever sets `SHIPPED` or `DELIVERED`.

- **[LOW] L3 — Marketing promises with no backing mechanism.** "Livraison 48h" appears on `Home.tsx:45,72`, `ProductDetail.tsx:270`, and `OrderConfirmation.tsx:80`; "un agent vous appellera dans les 24h" appears on `Checkout.tsx:268` and `OrderConfirmation.tsx:43,79`. Neither SLA has any field, timer, or worker behind it (no `call_due_at`, no escalation in `reservation_worker.py` or `event_worker.py`). Combined with **C1** (no shipped/delivered tracking) and **C2** (no visible phone number for the operator to call), these are currently three promises the operator team has no tooling to keep.

## 2. Operator journey — login → find a product → fix it → approve images → manage an order

### Login
Functional, with per-account lockout server-side. One cosmetic issue:

- **[LOW] L1 — Login page brand mismatch.** `admin/src/pages/Login.tsx:68-72` hardcodes the wordmark `"GHiR LAFFAiRE"`, tagline `"Fast · Reliable · Yours"`, and email placeholder `admin@ghirlaffaire.dz` — all pre-GLAIVE. Understandable in isolation (login happens before store selection, so it can't be per-store themed — store choice is a post-JWT step, `admin/src/lib/store.tsx`), but on a branch whose entire seeded catalog is GLAIVE gaming gear, a new operator's first screen names a different, unrelated brand.

### Find a product
This is where the newest admin feature quietly breaks:

- **[HIGH] H2 — The multi-store picker doesn't actually switch what "find a product" shows.** `admin/src/lib/store.tsx:62-67`'s `setCurrent()` calls `queryClient.invalidateQueries()` on every store switch — every query refetches, a spinner shows, it *looks* like it worked. But `GET /products` (list, `api/routes/products.py:70,83`), `GET /products/{id}` (`:181,185`), and `GET /products/graph` (`api/routes/catalog.py:87,93`) all resolve their store via the `require_store` dependency (the `Host` header), while the admin sends its selection as `x-store-id` on every request (`admin/src/lib/api.ts:37-38`) — a header these three endpoints never read. Net effect: an operator managing more than one store selects store B in the picker, watches the UI reload, and silently keeps looking at store A's product list, product detail, and relationship graph — with zero error, zero stale-data warning. (This is the user-facing consequence of the split already flagged architecturally in `audit/Architecture.md` §7.2; I'm restating it here because it lands on the single most common operator action — finding a product — not as an abstract scoping bug.)
- **[MEDIUM] M1 — The "Status" column in the product table doesn't show status.** `admin/src/pages/Products.tsx:216-219` renders `p.available > 0 ? 'N left' : 'OOS'` under a header literally labelled `<span>Status</span>` (`:171`), with the in-code comment *"// Status — not in list item, use available"* admitting the swap. But the backend already returns the real lifecycle `status` in every row of `GET /products` (`api/routes/products.py:150` `"status": r[8]`) — the admin's `ProductListItem` TypeScript interface (`admin/src/lib/api.ts:107-115`) simply never declares the field, so it's dropped on arrival. The page's own filter chips ("All / Needs Fix / Verified / Active", `Products.tsx:130-153`) filter by this exact field the table can't display, and 3 of the 7 possible statuses (`RAW`, `NORMALIZED`, `CLASSIFIED`, plus `ARCHIVED`) have no chip at all — an operator triaging the catalog has to open each product individually to learn which stage of the enrichment pipeline it's actually in.

### Fix it (ProductEditor)
Reasonable inline validation (required fields, slug pattern, price-comparison rules for the initial offer, `ProductEditor.tsx:106-130`), auto-slug derivation from name unless the user overrides it. No confirmed defects beyond the admin-wide language split (**M3**, below).

### Approve images
The best-executed admin page in the app: filter pills with live counts (Pending/Confirmed/All), a contextual hint explaining where the images came from and what "principale" means, broken-image detection with a fallback state (`ImageReview.tsx:186,201-205`), three clear per-image actions (Reject / Approve / Approve-as-primary). No defects found.

- **[MEDIUM] M3 — Mixed-language admin app.** `ImageReview.tsx` is entirely in French ("Validation des images", "Rejeter", "Approuver", "File globale," contextual hints). Every other admin page read for this audit — `Login.tsx`, `Products.tsx`, `ProductEditor.tsx`, `IssueExplorer.tsx`, `Orders.tsx`, `OrderDetail.tsx` — is entirely in English. An operator moving from "find/fix a product" straight into "approve images" (a normal single-session workflow) gets a language switch mid-task with no toggle or setting driving it — it's just inconsistent per-page authorship.

### Manage an order — the sharpest findings in the whole audit

- **[CRITICAL] C2 — The admin cannot see who to call or where to ship.** I traced the full read path for an order end-to-end. `api/services/orders.py:285-332` `fetch_order()` selects only `id, order_number, status, payment_status, payment_method, subtotal, shipping_cost, discount_amount, tax_amount, total, currency, created_at` plus `order_items` — it never joins `customers` and never selects `orders.shipping_address` (a `JSONB` column that is populated correctly at creation, `orders.py:153`). `OrderOut` (`api/models/schemas.py:148-163`) and the admin's own `OrderDetail` TypeScript type (`admin/src/lib/api.ts:451-455`) both omit `customer_name`, `customer_phone`, and `shipping_address` completely. Confirmed by a repo-wide grep: those three fields appear in `api/services/orders.py` **only** as write-side variables during order *creation* — never again, anywhere, on any read path. `OrderDetail.tsx`'s "Details" card (`:170-184`) shows Order ID, a **truncated customer UUID** (`order.customer_id.slice(0,12)…`), and Created date — nothing a human can act on. The admin `Orders.tsx` list has the same gap (`o.customer_id.slice(0,8)…`, `Orders.tsx:109`). Given the storefront's own promise — *"un agent vous appellera dans les 24h"* — this is not a nice-to-have field; it is the one piece of data the entire "manage an order" journey exists to surface, and it is absent everywhere in the admin.
- **[CRITICAL] C1 — There is no way, anywhere in the product, to record that an order was packed, shipped, or delivered.** `db/schema.sql:43-52` defines `order_status_enum` with `PACKED`, `SHIPPED`, `DELIVERED` as real values, and both frontends already have UI built for them: admin's `OrderDetail.tsx:10` progress bar (`ORDER_FLOW = ['PENDING','RESERVED','CONFIRMED','PACKED','SHIPPED','DELIVERED']`) and the storefront's customer-facing `OrderTracking.tsx:20-25` timeline (`Reçue → Confirmée → Expédiée → Livrée`). But `api/routes/orders.py` implements exactly two mutations — `confirm` (`RESERVED→CONFIRMED`) and `cancel` (`*→CANCELLED`) — and a repo-wide grep for `PACKED`/`SHIPPED`/`DELIVERED` across `api/`, `workers/`, and both frontends turns up only: the enum definition, the two UI files that *render* those states, and one guard clause in `cancel_order` (`orders.py:254`) that checks whether status is already `DELIVERED`. **No code anywhere ever writes those three values.** `shipped_at`/`delivered_at` columns exist in `orders` (`schema.sql:207-208`) and are even already exposed in the storefront's `TrackedOrder` type (`storefront/src/lib/api.ts:228-229`) — the write side was simply never built. Practically: every order in this system that isn't cancelled is permanently stuck at `CONFIRMED`. The admin's own progress bar and the customer's own tracking page both visually promise 3 more stages that literally cannot occur. This is the same root cause behind **L3**'s unbacked "Livraison 48h" promise.

## 3. Quick Wins (< 1 day each)

Ordered by severity of the problem they close.

1. **Surface customer contact + delivery address on the admin order view** — fixes **C2** (Critical). Add `c.full_name`, `c.phone`, `o.shipping_address` to the `SELECT`/`JOIN` in `fetch_order()` (`api/services/orders.py:285-332`), add the fields to `OrderOut` (`schemas.py`) and to admin's `OrderDetail` TS interface (`admin/src/lib/api.ts:451-455`), render a "Contact & delivery" card on `OrderDetail.tsx`. Contained to one service function, one schema, one UI card — the highest severity-to-effort ratio fix in this report. *Journey: operator → manage an order.*
2. **Translate/redirect checkout error messages to French** — fixes **H1** (High). Mirror the pattern already used correctly in `OrderTracking.tsx:113-116`: map the small, known set of `orders.py` `HTTPException` details (`offers not found…`, `offer … is inactive`, `cannot confirm/cancel order in status …`) and the generic `internal_error` case to French copy in `Checkout.tsx`'s `onError` handler, instead of passing `e.message` straight to `toast.error`. Isolated to `Checkout.tsx` + a handful of string literals in `orders.py`. *Journey: shopper → checkout.*
3. **Wire the real product status into the admin Products table** — fixes **M1** (Medium). Add `status: string` to `ProductListItem` in `admin/src/lib/api.ts:107-115` (the backend already returns it, `products.py:150`), render it as its own badge, add filter chips for the 3 missing statuses (`RAW`, `NORMALIZED`, `CLASSIFIED`) alongside the existing 4. *Journey: operator → find a product.*
4. **Fix the leftover "Ghir Laffaire" branding in storefront SEO tags** — fixes **M2** (Medium). Replace the brand string in the `<SEO description=…>` calls in `Checkout.tsx`, `Cart.tsx`, `OrderConfirmation.tsx`, `OrderTracking.tsx`, `SearchResults.tsx` with "GLAIVE." Pure text change, five files. *Journey: shopper → cart/checkout/confirmation/track.*
5. **Rebrand the admin login screen** — fixes **L1** (Low). Swap the "GHiR LAFFAiRE" wordmark, tagline, and `ghirlaffaire.dz` placeholder in `Login.tsx:68-85` for GLAIVE (or a store-neutral "GLstore Admin" if the login screen is meant to serve every tenant equally). *Journey: operator → login.*
6. **Stop promising a shipping-size discount that can't trigger** — fixes **L2** (Low), pairs with Deeper Change #2 below. Either remove the "livraison offerte dès 50 000 DZD" line from `Cart.tsx:85`/`EmptyState desc`, or — once a real shipping fee exists (Deeper Change #2) — make the threshold real. *Journey: shopper → land/cart.*

## 4. Deeper Changes

Ordered by severity / blast radius.

1. **Build the pack → ship → deliver transition** — fixes **C1** (Critical), the single most impactful gap in the operator journey. Needs: new route(s) on `api/routes/orders.py` (e.g. `POST /orders/{id}/pack`, `/ship`, `/deliver`, or one generic status-transition endpoint with a guard table mirroring `confirm_order`/`cancel_order`'s pattern), the matching service functions (populate `packed_at`/`shipped_at`/`delivered_at`, likely emit `order.shipped`/`order.delivered` events for the existing outbox), and admin `OrderDetail.tsx` buttons to drive each transition. This single change also unblocks the customer-facing tracking timeline (**C1**'s shopper-side symptom) and gives **L3**'s "48h delivery" promise something real to point at. *Journey: operator → manage an order; shopper → track order.*
2. **Design and implement real shipping-cost calculation** — fixes **C3** (Critical). Requires a business decision (flat rate vs. wilaya-tiered table) plus: either computing `shipping_cost` automatically at order creation (cleanest — the customer sees a true total before submitting), or building a genuine "agent adjusts it" workflow if manual pricing is intentional (a `PATCH /orders/{id}/shipping` endpoint, recomputation of `total` respecting the existing `total ≥ 0` and `total = subtotal + shipping − discount` invariants, and an editable field on admin `OrderDetail.tsx` in place of today's read-only row). Until either exists, the honest short-term move is to stop implying a variable/agent-set fee in the copy (see Quick Win #6). *Journey: shopper → cart/checkout; operator → manage an order.*
3. **Make the admin store picker trustworthy** — fixes **H2** (High). Switch `GET /products`, `GET /products/{id}` (`products.py:70,181`), and `GET /products/graph` (`catalog.py:87`) from `require_store` to `require_admin_store_for`, matching every other admin-facing route in the same files (offers CRUD, images, enrichment, orders already do this correctly). Non-trivial because these three endpoints are presumably shared with the public storefront's own product-detail/catalog-graph usage — needs a careful split (public path keeps `require_store`, admin path gets its own `require_admin_store_for` route or an explicit admin-vs-public branch) and regression coverage before shipping, since there is currently no route-level test at all (per `audit/Architecture.md` §7.5) to catch a mistake here. *Journey: operator → find a product.*
4. **Standardize the admin app on one operational language** — fixes **M3** (Medium). Given the storefront is fully French and the business locale is Algeria, the natural choice is French throughout admin too (or a proper i18n layer if English-speaking staff also use it). This is a full content pass across all 14 admin pages, not a single-file fix, and should probably land alongside Deeper Change #1 (new copy for pack/ship/deliver buttons) rather than as its own separate release. *Journey: operator → all steps.*
5. **Give operators a real activity trail on an order** — supports **L3**, adjacent to **C1**. Right now a status enum with no history is the only record of what happened to an order — no log of confirm calls made, no note field surfaced beyond the one-time cancellation reason. The schema already has an unused `audit_log` table (flagged as dead code in `audit/Architecture.md` §7.6); wiring order-status transitions to write into it (or a lighter dedicated `order_events` view) would let an operator answer "did we call this customer yet?" without relying on memory. *Journey: operator → manage an order.*
